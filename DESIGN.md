# SeekerShark interface

Current implementation direction for the Android app. The black, matte red, gray and white palette was explicitly requested by the user.

- Black background (`#050505`), neutral near-black surfaces (`#111111`), matte red capture actions (`#9e3838`), muted red accents (`#d06a67`), and gray/white text. No cyan, green, purple, colored glow, or glossy button treatment. Protocol badges use red and neutral gray variations while retaining their text labels.
- Developer console, not a landing page: fixed-height app shell, compact capture/file toolbar, inline counters, filter, and independently scrolling packet list. No hero titles, marketing copy, statistic cards, brand taglines or repetitive explanations. Desktop uses compact tabs; mobile uses bottom navigation with safe-area padding.
- Mobile controls have at least 44×44 px touch targets. Capture and file actions use visible labels and bordered surfaces; mobile navigation highlights the current tab. Packet details have a persistent top Back button and a full-width bottom Back button outside the scrolling content.
- Back navigation restores the originating view, filter and scroll position, including analysis drill-downs. A bounded 32-entry stack stays local to the app. The official Tauri Android Back listener is installed only while an in-app destination exists; at the root Android retains its normal behavior.
- Android fits the entire WebView inside system-bar and display-cutout insets in MainActivity, including HTML dialogs. Consumed insets avoid double padding; CSS safe-area variables also support browser layouts. Keep keyboard resizing enabled.
- Scan is a fourth navigation destination. Keep configuration compact, with visible Target/TCP ports labels, presets, Fast TCP/Service probes modes, and fixed Scan/Stop/Export JSON actions above the mobile navigation. Preserve form state and scan jobs across navigation. Distinguish response evidence from port hints and show real progress/counters; the browser never fabricates a scan.
- Nearby adds a fifth destination in the same console style. Use real participant discovery, explicit code confirmation and capture sharing, a separate received-capture inbox, and a fixed Start/Stop action. Preserve its state across tabs; distinguish a shared capture from the local VPN source. Explain the browser limitation without inventing devices or transfer activity. Opening a received capture requires the local capture to be stopped.
- Radio adds a sixth destination with Bluetooth and Wi-Fi sensor subviews. BLE shows bounded address/advertising-set observations and Android scan-report counts; never label these as physical phone counts or convert RSSI to distance. Keep expanded observation details, filters and source selection across polling/navigation. Wi-Fi initially imports validated sensor JSON reports and labels live/USB capture unavailable. Keep six bottom-navigation targets usable at 320 px.
- Raw view is the default. The explicit Beautify switch is available in the toolbar and inspector, persists locally, and changes only presentation. It adds readable packet summaries and field explanations, and formats captured plaintext HTTP/JSON payloads. TLS/QUIC remain encrypted. Do not infer TCP stream completeness or negotiated TLS versions from partial metadata.
- Demo mode is static, local, and explicitly labeled. It never animates simulated traffic or pretends to be a live capture.
- Filters support combined `proto:`, `port:`, `host:` and text terms. They are a documented subset, not Wireshark display filters.
- Render at most 150 packet rows initially, with explicit pagination. Keep unchanged packet references across capture updates. Skip background polling when the document is hidden. Native capture runs independently.
- Packet layers load on selection. Hex starts at 256 bytes and expands by request. Android export saves through the native download API.
- Use English for UI labels, accessibility text, Beautify explanations, demo metadata, native errors and notifications, code comments, documentation, and workflow messages. Use English number grouping and declare `lang="en"` in HTML. Preserve captured network content verbatim.
- Use system fonts and local SVG icons. No remote font or asset requests. Respect reduced motion.
- Generate icons with `bunx tauri icon src-tauri/icons/manifest.json`; the manifest preserves the black adaptive-icon background. Android day/night themes, splash background and system bars use the same black/red/gray palette.

Verification performed in Chromium at 1440×1050, 393×852 and 320×780: packet filtering, protocol drill-down, layer/hex inspector, Escape dismissal, real demo PCAP download, clear/reload, Beautify switching/persistence, actual JSON formatting, encrypted-payload boundaries, and browser runtime limitation messages. Touch-target sizes, top/bottom inspector returns, filter/scroll restoration, session returns, analysis drill-downs and filter-help dismissal are covered by the browser suite. CSS safe-area tests simulate top/bottom insets; they do not verify Android system bars or gestures. No JavaScript errors or horizontal overflow were observed. Native Android Back gestures, system-bar/cutout layout, VPN, file picker and system downloads require device verification.

Reproduce the browser smoke checks with `bunx playwright install chromium` and `bun run test:ui`. If using an existing local Chromium installation, set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium` for the test command. The suite starts Vite on port 1421, checks desktop and narrow touch layouts, validates the exported demo PCAP, and fails on JavaScript errors. It does not verify the Android VPN or native download path.
